Architecture

Nine layers.
Each one has a reason.

OVAT sits between you and OpenVINO Model Server. OVMS does the inference. OVAT decides which model, which device, which parser and which tools, then runs the loop and the server for you. This page walks the layers in order, the way a request meets them.

Layer 1 CLI and configuration

A strict file, read in one place

Every command is a Python function that Typer turns into ovat <command> from its type hints. There are eleven: run, chat, index, init, doctor, setup, serve, models, bench, telemetry and tui. A bare ovat opens the terminal UI.

The config is strict. WorkflowConfig is a pydantic model that forbids unknown keys. Think of it as a struct with a constructor that refuses bad input. A typo such as max_iteration fails at once, by name, instead of being ignored while the default quietly stays in charge.

Only one function loads it. _load_config() in cli/main.py turns three different failures into three plain sentences: the file is missing, the YAML does not parse, or the schema does not match. An empty file used to produce a Python internals error; now it is a schema error that names the missing model section.

Model text is data, not markup. Every value OVAT did not write goes through esc() before printing. A model answer ending in [/INST] once crashed ovat run, because the console library read it as a style tag.

file missing

Names the path it looked for, and notices when a question was typed where the file name belongs.

bad YAML

Gives the line and column where parsing stopped.

schema error

Lists each field and what was wrong with it, and explains that unknown keys are rejected on purpose.

Layer 2 Framework integration

Four engines behind one method

Every engine exposes the same .run(text) -> text. The factory hands back one of them and the CLI never knows which. In C++ terms it is one interface with four implementations.

Two things keep the four honest. Tool arguments for every engine are derived from each tool's own SCHEMA by agent/arg_models.py; a hand-kept second list once let a tool work on one engine and crash on another. And the server connection (URL, model, timeout, sampling) is described once in providers/backend.py; temperature was once set in two engines and missing in the other two for a whole release.

The LangChain, LlamaIndex and Agents SDK engines run their own event loop and refuse to start inside one that already exists. That is on purpose: nesting would deadlock.

Layer 3 Agent core

The loop that gives the model hands

A model can only write text. The native loop in agent/loop.py is what turns its written request into a real function call. Each round has four beats: ask, read, act, report. Below, one real question from the RAG example goes round twice.

Memory is just a list. A model forgets everything between calls, so agent/session.py keeps the conversation and resends it each time. It is thread-safe because the terminal UI streams an answer on one thread while you can save or load on another; it copies the list under a lock and writes the file outside it.

Small models get some slack. Arguments wrapped in a Markdown code fence are unwrapped before parsing, and a slightly wrong file path is swapped for the closest real file, always with a note in front of the result saying so.

Layer 4 Provider abstraction

Sockets and plugs

providers/base.py defines four abstract classes: the sockets. Each concrete class beside it is a plug. The config names a plug as a string, so swapping a backend is a YAML edit and nothing above this layer changes.

LLMProvider

  • ovms OpenAI SDK to OVMS /v3. Can call tools.
  • genai openvino_genai in your process. No tools, no server.

EmbeddingsProvider

  • genai Local text embedding pipeline, bge-small.
  • ovms OVMS /v3/embeddings.

RetrieverProvider

  • sqlite-vec Vectors and text on disk; survives restarts.
  • memory numpy in memory; leaves nothing behind.

VLMProvider

  • genai OpenVINO VLMPipeline, used by describe_image.

Document search, end to end

RAG means retrieval-augmented generation: find the right passages first, then let the model answer from them. OVAT does it in two phases. ovat index runs once; search_docs runs whenever the model asks.

One fix worth knowing. On SQLite older than 3.38 (Ubuntu 22.04 ships 3.37) a LIMIT ? never reached the vector table, so search returned nothing and the agent answered confidently with no citation. The query now uses sqlite-vec's own k = ? form, and CI runs on Ubuntu 22.04 to keep it that way.

Layer 5 Tools and MCP

Three built-in tools, and any MCP server

Each built-in tool follows one pattern: a plain *_impl() function you can unit test, a SCHEMA dictionary beside it that is the tool's contract, and a FastMCP wrapper so the same file also runs as a standalone MCP server.

MCP is a standard way for a program to offer tools to any agent. OVAT is an MCP client too: declare type: mcp_stdio, and the factory starts the server, asks it which tools it offers, and hands them to the loop in the same shape as the built-ins. The loop cannot tell them apart.

Built-in tools

The MCP client is sync over async. The mcp SDK is asynchronous, the loop is not. Each server gets one background thread with one event loop and one manager coroutine that connects, serves and unwinds. Closing sets an event and lets that coroutine unwind itself, because the SDK's cancel scopes must be entered and left by the same task.

A separate process needs the config, not the object. An MCP server is a new Python process, and objects do not cross that line. An MCP-served search_docs was stuck in stub mode, 104 characters of placeholder, while the built-in path returned 1932 real ones from the same index. The server now takes --config and builds its own retriever.

Layer 6 Orchestration

Not built, on purpose

Agent-to-agent (A2A) orchestration was a stretch goal in the proposal, and the core toolkit was always meant to work without it. The owner scoped it out. It is listed here so the numbering matches the design document.

Layer 7 Observability

Measurements that do not lie

Where a number comes from (a source) and where it goes (a sink) are separate contracts, so any source feeds any sink. Six sources and three sinks need nine small classes and one collector, not eighteen wirings. The collector ticks on its own thread, so a stuck sensor cannot slow the agent.

Absent is not zero

No token count from the server is null, shown as a dash. A 0 would read as "used no tokens", and a benchmark built on it is quietly wrong.

An unavailable source says why

On macOS the Intel row reads "Intel Unified Telemetry does not run on macOS" instead of showing zeros. A missing sensor and an idle one look the same in a graph.

Peak memory is sampled during the run

A reading taken afterwards misses the peak, because Python has already freed the big allocations. With OVMS serving, the model's memory lives in the server process, not in OVAT.

ovat bench runs each engine in a fresh process for the same reason. In one shared process the native engine read 465.8 MB when it ran first and 1155.6 MB when it ran last. A benchmark that changes its answer when you reorder the inputs is not measuring the inputs.

Layer 8 Deployment and serving

Getting OVMS installed, started and stopped

ovat setup picks the right OVMS archive for your OS (and, on Linux, your distribution), checks its SHA-256, and unpacks it into ~/.ovat/ovms. Nothing is added to PATH. It always takes the python_on build: the python_off build cannot do tool calling, which gives an agent that answers fluently and never calls a tool. The pinned version is OVMS 2026.4.1.

It is a command rather than part of pip install because the archive is 126 to 185 MB, Linux needs three different builds, wheels have no post-install step, and macOS has no build at all.

Where OVAT looks for the server, in order

  1. model.ovms_binaryin your YAML
  2. OVAT_OVMSenvironment variable
  3. PATHthe classic place
  4. ./ovms ~/.ovat/ovms ~/ovms_windows ~/ovms C:\ovmsknown folders

A stall budget, not a deadline

The first ovat serve downloads the model, about 185 s for Qwen3.5-4B and longer on a slow link. The clock resets whenever the log or the model folder grows, and gives up only after 300 s of no progress at all.

Logs go to a file

A pipe nobody reads fills its buffer, around 64 KB, and the server freezes. OVMS writes to ovms.log instead.

Stop checks identity

ovat serve --stop reads ovms.pid and confirms the process really is OVMS before signalling it, because a stale PID can belong to another program.

Layer 9 OpenVINO runtime and hardware

Each model goes to the right chip

core/device_manager.py asks OpenVINO which devices exist, then applies a routing table. The same code runs on a Mac and an AI PC; only the device list changes. Pick a machine to see the routes.

Across layers Failure design

Four ways a tool call goes wrong, each with a name

All four end the same way: the agent answers fluently and has called nothing. That is the hardest kind of broken to notice, so the loop detects each one and sets a flag in the trace. ovat bench scores on those flags, not on the answer text.

truncated

The reply was cut at max_tokens (4096 by default), so any tool-call markup is a fragment. Detected from finish_reason: "length", so it is never blamed on the parser.

undecoded_tool_call

Raw <tool_call> markup reached the answer: no parser matched, or the model wrote the call malformed. Usually the wrong tool_parser.

empty_answer

Nothing is left once the reasoning is removed. The parser swallowed the reply.

a real answer

Text remains, with no markup in it. The run exits 0. Every other case exits non-zero, writes its trace, and cleans up.

The broken markup is deliberately not repaired into a tool call. Guessing at broken output trades a loud failure for a silent wrong answer.

Across layers Design rules

Four rules, each paid for by a real bug

Optional stays optional

The terminal UI and the three frameworks are extras. A test fails if a base install imports textual, langchain, llama_index or the Agents SDK.

The core ignores presentation

The loop never imports the CLI. Text helpers both need live in a neutral ovat/text.py.

One place per fact

Colours in ui.PALETTE, tool contracts in each SCHEMA, the backend in LLMBackend, config loading in _load_config.

Errors are for people

A failure becomes a sentence the model or the person can act on, never a bare traceback on the CLI or in the UI.
