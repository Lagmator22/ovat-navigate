Is it chance? McNemar's test, which compares paired right and wrong answers on the same questions, gives p = 0.0001. That is why OVAT pins OVMS 2026.4.1 in core/ovms_installer.py, and why ovat setup and doctor read the installed version.

2026.2.1: up to 5 different answers in 5 runs at temperature 0, the worst case shown. A fixed seed: 42 did not help: 0 of 20 attempts matched across two identical arms.

None of the three got a single answer right that the plain config got wrong (p >= 0.5), so all three stay off by default.

About auto: on OVMS 2026.2.1 it selected no parser at all and printed the raw tool call as the answer. On 2026.4.1 it detects qwen3coder. OVAT still names the parser, so an older server someone installed by hand also works.

KV cache static size, three runs per arm

A full cache costs about ten times the latency

Seconds for one LangChain tool-calling test

The KV cache is the model's working memory for a conversation. These runs fixed its size with --cache_size.

1 GB, 13.9% full16 s
1 GB, 100% full, tool call failed151 s
1 GB, 100% full146 s
8 GB, under 2% full, 3 runs13 to 18 s
04080120160 s

What it shows: a full cache reproducibly costs about 10x the time, which matches the preemption and recompute that OVMS documents.

What it does not show: that a full cache breaks tool calls. The failure appeared once at 100%, but the same reading also passed, so at three runs per arm that stays unproven. And unless the size is fixed, OVMS grows the cache as it goes, so "100% full" on its own means little.

The NPU pipeline is compiled to fixed shapes, so the total length has a ceiling however the split falls. The reply was cut mid-sentence and labelled finish_reason: "unknown", not "length".

A tool call still being written when the cap lands is cut in half, which looks exactly like a parser failure. For an agent, whose prompt grows every round, the prompt length setting matters most; OVAT raises the NPU default from 1024 to 4096.

Not verified: that group quantisation is the cause of the stock export's failure. The compiler's own message was about duplicated names. What is verified is that the channel-wise export compiles and the stock one does not.

Four engines, one question, one server

An ovat bench run of the RAG example (the screenshot is in the guide): Qwen3.5-4B on the Arc 140V GPU, each engine in its own process. One run per engine, so read it as a snapshot, not a ranking.

Build time was 0.734 s for native, 15.185 s for react, 1.372 s for llamaindex and 1.132 s for openai-agents. All four answered ok, and all four recorded prompt and completion tokens from OVMS's usage field: 2002/485, 1410/387, 1456/224 and 1418/218, with 2, 1, 1 and 1 tool calls. An earlier run of the same example answered in 14.6, 164.9, 17.6 and 10.3 s, so a single run says little about which engine is faster.

Quality every push

800+ tests, chosen platforms

The suite needs no server and no model; tests that do are marked and skip themselves. Every fix ships with a test that fails when the fix is backed out. The CI matrix is picked to open as many differences between machines at once as possible, because every bug the project shipped lived in a gap between two machines.
